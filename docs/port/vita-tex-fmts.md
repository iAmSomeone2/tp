# PS Vita Texture Formats

The GXM texture formats from the vitasdk `SceGxm` docs (lists below), and how the bake maps every GX texture format to them without changing a texel (next section).

## Mapping GX formats to GXM (lossless)

Rule: the baked texture must decode to exactly the RGBA values GX would produce. Where GXM has no format that holds a GX format exactly, the bake widens it.

GXM swizzle names list components from the most significant bit down, in the order A, B, G, R (e.g. `U8_1RRR` = alpha 1, colour = R = `L8`; `U8U8U8U8_ABGR` = `A8B8G8R8`, bytes R, G, B, A in memory). GX intensity formats return the intensity in all four channels, alpha included. GX widens 3-, 4-, 5- and 6-bit values to 8 bits by repeating their bits.

| GX format | bpp | GXM format | bpp | Conversion |
|---|---:|---|---:|---|
| `I4` | 4 | `U8_RRRR` | 8 | Widen each texel: `i * 17`. GXM has no 4-bit single-channel format. |
| `I8` | 8 | `U8_RRRR` | 8 | Untile only. |
| `IA4` | 8 | `U8U8_RGGG` (`A8L8`) | 16 | Widen: alpha (high nibble) and intensity (low nibble), each `* 17`, written as bytes A, I. |
| `IA8` | 16 | `U8U8_RGGG` (`A8L8`) | 16 | Untile only: GX's big-endian word already gives the bytes A, I in memory, which is `A8L8`. |
| `RGB565` | 16 | `U5U6U5_RGB` (`R5G6B5`) | 16 | Untile, byte-swap each 16-bit texel. |
| `RGB5A3` | 16 | `X1U5U5U5_1RGB` if *every* texel has the top bit set (opaque RGB555); otherwise `U8U8U8U8_ABGR` | 16 / 32 | The bake scans each texture. Opaque case: byte-swap only, and the ignored top bit is GX's mode flag. Otherwise expand each texel (RGB555, or A3 RGB444) to 8888. `U4U4U4U4` would not be exact: 3-bit alpha widens to 0, 36, 73, …, which are not multiples of 17. |
| `RGBA8` | 32 | `U8U8U8U8_ABGR` | 32 | Untile and merge the AR and GB halves of each 4×4 tile. |
| `CMPR` | 4 | `UBC1_ABGR` | 4 | Same encoding as BC1. Reorder the 4×4 blocks (GX groups 2×2 of them in 8×8 tiles), byte-swap the two RGB565 endpoints, and reverse the order of the 2-bit indices within each byte. Use `_ABGR`, not `_1BGR`, so that index 3 in three-colour mode stays transparent. |
| `C4` | 4 | `P4_ABGR` | 4 | Indices unchanged except for nibble order (to check: GX puts the first texel in the high nibble). The palette is widened to 32-bit entries from its TLUT format (`IA8` → I, I, I, A; `RGB565`; `RGB5A3`), which is exact for all three. |
| `C8` | 8 | `P8_ABGR` | 8 | As `C4`. |
| `C14X2` | 16 | the direct format of its TLUT (`U8U8_RGGG`, `U5U6U5_RGB`, or the `RGB5A3` rule) | 16 / 32 | GXM palettes only have 16 or 256 entries, so the palette is looked up during the bake. |

Notes:

* **Every format is lossless.** Only `I4`, `IA4` and `RGB5A3` with translucent texels get bigger.
* **The ordering details need a hardware check.** These are which of `U5U6U5_RGB`/`_BGR` puts R in the top bits, and the `P4` nibble order. A small test texture per format on the Vita settles both.
* **Memory layout:** the MVP bake writes linear data (`SCE_GXM_TEXTURE_LINEAR`), which works on the dev PC and the Vita alike. GXM's swizzled layouts are faster on the Vita and can be a later, Vita-only bake option. They need power-of-two sizes, and almost all of the game's textures have them.
* **Host GPUs:** the formats map one to one to the desktop formats R8, RG8, B5G6R5, RGBA8 and BC1. Swizzles such as `RRRR` or `RGGG` need component swizzling in the texture view; where the host backend lacks it, the generated shader applies the swizzle instead. The bake records what each texture means (intensity, luminance + alpha, colour), not a GXM enum, so each backend picks its own format.
* **Depth formats** (`Z8`, `Z16`, `Z24X8`) only occur in code, for render targets and copies, not in data files. They are the GX layer's concern, not the bake's.
* **Still unknown:** how often each format occurs on the disc. Counting it is a small extension to `tools/gx_shaders/scan.py` and would show how much the widening costs.
